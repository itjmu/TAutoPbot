## 3. Что пользователь попросил и что уже реализовано

### Конкурс и розыгрыш

Это **два режима одного бота**, а не два отдельных приложения.

**Конкурс:** тип → канал → приз → свой пост или шаблон №1 → количество победителей → дата окончания → контакт выдачи → условия → предпросмотр/запуск. Побеждают участники с наибольшим количеством учтённых приглашённых друзей.

**Розыгрыш:** аналогичный сценарий с шаблоном №2; случайный выбор без повторения победителей. Приглашённые друзья увеличивают вес участника.

Требования пользователя:

- Подписки на каналы/группы; ссылки можно включать в текст или отдельные кнопки.
- Последняя кнопка — «Участвовать · количество». Она проверяет подписки **в самом канале**, отвечает всплывающим уведомлением и не перенаправляет в личный чат.
- Капча и реферальные действия могут выполняться внутри бота. Если они требуются, публичный callback сообщает, что надо сделать.
- Приглашения могут засчитываться за участие друзей либо за вступление по персональной ссылке в канал публикации.
- По окончании нужно изменить **тот же пост**, указать победителей и контакт выдачи. Без контакта — сообщение, что с победителями свяжутся.
- Создатель получает список победителей в личку.
- Повторные callback, перезапуски и повторные попытки доставки не должны заново разыгрывать победителей.

Всё перечисленное реализовано в коде и покрывается офлайн-тестами. Сквозная проверка с настоящими Telegram-аккаунтами и реальными правами канала ещё нужна.

### Free и Premium

| Возможность | Free | Premium |
|---|---:|---:|
| Подключённые каналы/группы | 10 | 20 |
| Источники | 2 | 10 |
| Создание обычных постов | 3/день | Без ограничения |

Это значения по умолчанию. Администратор может изменить поддерживаемые лимиты через настройки тарифов; актуальные значения берутся из `app_settings`. `-1` означает отсутствие лимита там, где это допустимо. Обычный бесцветный стиль кнопки также доступен. Нельзя обещать произвольный RGB: используются стили Telegram `primary`, `success`, `danger`.

**Пробного Premium нет.** `start_trial()` возвращает False, `TRIAL_DAYS=0`; старый callback пробного периода не активирует подписку. Реферальные бесплатные награды Premium на чистой базе по умолчанию равны нулю. Не возвращать автоматическую раздачу пробного Premium.

Суточные квоты считают дни **UTC**, независимо от часового пояса пользователя. Каждое видео плейлиста считается отдельно; части одного видео не умножают расход. MP3 из видео расходует квоту; изображения — нет. Ошибка/отмена извлечения возвращает резерв, но успешное скачивание с последующей ошибкой отправки Telegram уже считается использованным.

## 4. Приоритетная незавершённая диагностика: скачивание

Последняя жалоба: «перепровер скачки чето перестал работат не скачает ничего».

### Установленные факты

В рабочей БД на момент диагностики были две записи `downloads` со статусом `failed` и общим сообщением загрузчика:

1. VK Video: `https://m.vkvideo.ru/video-219382335_456241384`.
2. YouTube: `https://www.youtube.com/watch?v=sBdRVt385pE`.

Обе ссылки проходили inspection, сохранялись с backend=`yt` и списком качеств. Значит, проблема не сводилась к распознаванию ссылки или отсутствию кнопок.

Проверки в предыдущем чате:

- `download_files()` реально скачал оба видео в 144p во временные каталоги.
- Прямой запуск полного `download_worker_main()` успешно скачал, обработал и разделил VK-видео на четыре MP4-части; для YouTube получили две части.
- Обычный `run_download_worker()` один раз воспроизвёл общий сбой на VK, но исходное исключение тогда не было сохранено.
- Позднее `run_download_worker()` успешно обработал YouTube в 144p: два файла размером **42 093 170** и **41 580 136** байт.
- Локально сгенерированное видео успешно прошло `prepare_video()` и `upload_metadata()`.
- Проверки скачивания не отправляли эти файлы в реальный Telegram. Реальная отправка пользователю не подтверждена.
- Эти проверки не означают, что все качества, соцсети и публикации работают. Проверяли конкретные видео, главным образом 144p.

### Последние изменения, уже сохранённые в файлах

1. `services/progress.py::write_worker_progress()`:
   - запись `progress.tmp` и замена `progress.json` обёрнуты в обработку `OSError`;
   - временная блокировка служебного файла больше не должна обрывать скачивание;
   - отметка времени успешной записи обновляется только после успеха, поэтому следующая попытка не подавляется throttling.
2. `app/downloader.py::temporary_size()`:
   - вынесен подсчёт временных файлов;
   - `FileNotFoundError` при одновременном переименовании/удалении части yt-dlp игнорируется;
   - контроль общего размера сохранён.
3. Worker печатает traceback в stderr; родитель логирует последние 4000 символов stderr при ответе `ok=False`. Пользователь по-прежнему получает понятное сообщение.
4. Добавлены тесты на блокировку progress-файла и исчезающий файл при подсчёте размера.

**Уровень уверенности:** дефекты обработки progress/переименования файлов исправлены и проверены тестами. Но именно их причинная связь с исходными двумя сбоями пользователя **не доказана traceback исходного сбоя**. Не говорить, что точная причина всех проблем окончательно установлена.

Рекомендуемое продолжение:

1. Посмотреть актуальный код последних изменений; базу читать только в режиме read-only для диагностики.
2. Проверить полный worker с progress на проблемной ссылке. Использовать временную папку, не сохранять токены/cookies в выводе.

## 5. Архитектура: слои и ответственность

```text
bot.py
  -> app.application.main()
     -> RuntimeLock -> init_db/migrations -> recover
     -> Bot + Dispatcher(SQLiteStorage, SimpleEventIsolation)
     -> app.routing.build_router() + Guard
     -> features/* handlers <-> FSM + services + SQLite
     -> APScheduler jobs
     -> start_polling(allowed_updates=resolve_used_update_types())

Скачивание:
message/link -> common.offer_incoming / downloads.download_url_message
  -> BackgroundJobs -> inspect worker -> downloads row + quality buttons
  -> dl callback -> BackgroundJobs -> download worker subprocess
  -> yt-dlp / TikTok embed / gallery-dl / direct HTTP
  -> FFmpeg preparation -> ProgressInputFile -> Telegram -> draft/target picker
```

## 6. Важные маршруты и исправления последних обращений

### Частный канал молчал после «Выбрать канал и добавить бота»

Старая кнопка была URL `startchannel`, а обработчик ожидал `my_chat_member` в течение 15 минут. Повторное добавление уже назначенного бота не обеспечивало новый сигнал выбора канала.

Текущий код:

- `channel:add` показывает меню; кнопка канала имеет callback `channel:picker`.
- `channel_picker()` присылает ReplyKeyboard с `KeyboardButtonRequestChat(request_id=701, chat_is_channel=True)`.
- Запрашиваются права администратора пользователя/бота; `chat_has_username` не ограничен, поэтому доступны частные каналы.
- `channel_shared()` получает `chat_shared.chat_id`, запрашивает chat и вызывает `connect_channel()`.
- `register_channel()` повторно проверяет права на сервере, лимит, конфликт владельца и делает upsert без дубликата.
- После успеха временная reply-клавиатура убирается, показывается подтверждение и меню каналов.
- На входе в picker удаляется ожидание старого my_chat_member setup, чтобы не подключать дважды двумя путями.
- Старый `my_chat_member` остаётся для прежнего сценария и добавления группы; пересылка сообщения/@username тоже работают.
- Тесты: private picker, подключение без membership event, повторный выбор, запрет без admin rights.

В используемой версии aiogram `ChatAdministratorRights` требует также `can_send_welcome_messages`; сейчас передаётся False. Не удалять без проверки версии.

**Документация README в части Add channel частично описывает прежний сценарий**. Для актуального поведения ориентироваться на `channels.py` и этот раздел. Реальная проверка новой кнопки в Telegram не зафиксирована.

### «Unable to serialize unknown type: aiogram.client.default.Default»

Ошибка была в сохранении входящего Message в `common.offer_incoming()`:

```python
m.model_dump_json(exclude_none=True, exclude_defaults=True)
```

`exclude_defaults=True` добавлен, чтобы не сериализовать aiogram Default, например внутри `LinkPreviewOptions`. Меню уже существовало, но ошибка мешала его показать. При сообщении со внешней ссылкой предлагаются **скачать / создать пост / пропустить**.

Данные лежат в `incoming`: owner_id, message_json, links_json, post_id. Callback `in:<id>:<action>` проверяет владельца. При создании поста восстановление идёт через `Message.model_validate_json`; существующий post_id повторно используется. При нескольких ссылках выводится выбор.

Регрессионный тест использует реальный Message с LinkPreviewOptions и проверяет round-trip и все три действия. Не заменять сериализацию всего объекта на `str()`.

## 7. Скачивание: детали и ограничения

- `app/downloader.py` — URL validation, backend selection, cookies, formats, worker lifecycle.
- `app/download_worker.py` — отдельная точка входа процесса. Worker не открывает рабочую БД; окружение переопределяет DB_FILE=:memory:, BOT_TOKEN пустой, ADMIN_ID=0.
- В `downloads.py` Semaphore(2): два media jobs одновременно. Один пользователь не запускает параллельно несколько download jobs.
- Inspection timeout: 180 секунд; download timeout: 3600 секунд.
- Default source limit: 1 000 000 000 bytes; temporary total: 4 000 000 000 bytes; Telegram part: 49 000 000 bytes.
- Проверяется, что итоговые файлы внутри выделенного temp-каталога и не превышают лимиты.
- Запрещены file:// и локальные/приватные адреса; network guard проверяет DNS и реальные соединения. Не отключать SSRF-защиту для «починки».
- Поддержанные протоколы форматов ограничены HTTP(S), native HLS, HTTP DASH segments; DRM/live не поддерживаются.
- Media fallback при TelegramBadRequest: отправка документом. ProgressInputFile закрывает readers при отмене.
- Worker принудительно останавливается вместе с дочерними процессами: taskkill /T /F на Windows, process group на Linux.
- `download_deliveries` записывает отправленные части/завершённые entries, чтобы повтор не присылал уже учтённое.
- Crash между фактической отправкой Telegram и записью message_id всё ещё может дать дубликат. Exactly-once upload не обещать.
- `/stopdownload`, `/stop_download`, кнопки остановки — отмена фоновой задачи. `/cancel` относится к текущему FSM-вводу, это не то же самое.

### TikTok/Instagram и cookies

Ранее пользователь присылал:

- `https://vt.tiktok.com/ZSmXc2S7D/`
- `https://vm.tiktok.com/ZS9LwP84FH6KV-NszZB`
- Ошибку Instagram empty media response для shortcode `DdWRcjRNIGG`.

Уже добавлены resolution коротких TikTok-ссылок, fallback официального embedded player, gallery-dl, перезапрос подписанных media URLs при скачивании. В одной прошлой проверке видео TikTok скачалось; другая короткая ссылка вела на главную страницу и требовала новой ссылки. Не считать результат вечным: сайты и ссылки меняются.

Cookies только из явно настроенных Netscape-файлов. Приоритет site-specific над общим. Браузерные сессии не импортируются автоматически, shared cookies не перезаписываются после задания.

Переменные: `DOWNLOAD_COOKIES_FILE`, `INSTAGRAM_COOKIES_FILE`, `TIKTOK_COOKIES_FILE`, `YOUTUBE_COOKIES_FILE`, `TWITTER_COOKIES_FILE`, `FACEBOOK_COOKIES_FILE`, `VK_COOKIES_FILE`, `REDDIT_COOKIES_FILE`.

Приватность, удаление публикации, геоблокировка, rate limit, login, DRM и неподдержанный сайт могут объективно мешать скачиванию. Не обещать «все соцсети без ошибок».

## 8. Giveaway: целостность и доставка

- Основная таблица `contests`; добавлены giveaway_type, prize_title, claim_contact, subscription_layout, referral_target, displayed_count.
- `contest_entries` — участие/base_valid/пригласивший; `contest_winners` — уже определённые победители.
- `contest_invites` — персональные invite links; `contest_channel_referrals` — вступления и активность, есть индекс для подсчёта.
- `contest_outbox` отделяет фиксацию результата от отправки сообщений.
- Режим ranking — конкурс; weighted — розыгрыш. Legacy ranking мигрируется в giveaway_type contest.
- Счётчик учитывает валидных незаблокированных участников с выполненным минимумом приглашений.
- Перед финальным выбором перепроверяются подписки. Ошибка Telegram не должна автоматически дисквалифицировать участника.
- Победители записываются транзакционно; повтор доставки не запускает новый random draw.
- Public Participate проверяет, что callback пришёл с сохранённого chat/message этого конкурса.
- Счётчик и финальное изменение сообщения используют общую asyncio-блокировку на конкурс, чтобы позднее обновление счётчика не затёрло результат.
- Результат меняет text/caption исходного post, убирает кнопки. Для медиа проверяется лимит 1024 UTF-16; есть тест 20 победителей с Unicode.
- Ошибки редактирования результата повторяются через outbox; неуверенно завершённые отправки новых сообщений не повторяются слепо.
- Неопределённую публикацию восстанавливают через пересланный оригинал либо указанный message_id, а не просто сменой status.
- При отмене опубликованного giveaway исходный пост должен получить отметку отмены.

## 9. База данных и защита данных

Схема находится в `app/database.py`; читать её перед SQL-изменениями. Группы данных:

- пользователи/Premium/квоты/настройки и рефералы;
- channels, условия, ответы, заявки;
- posts и расписания, шаблоны, источники и очереди альбомов;
- incoming, downloads, download_deliveries;
- contests, entries, winners, outbox, invites, channel referrals;
- FSM и runtime lock.

Это карта областей, не полный SQL schema dump. Не придумывать столбцы по этому описанию.

`database.execute()` учитывает внешнюю транзакцию; `database.atomic()` использовать для связанных изменений. На диске WAL, поэтому обычное копирование одного bot.db при работающем процессе не заменяет корректный backup.

**Сброс уже сделан 19 сентября 2026**:

```text
backups/bot-20260919T023556537155Z.sqlite3
```

После сброса integrity check был OK; users/channels/posts/contests были пусты. Позже БД наполнилась снова (как минимум появились downloads). Не называть её сейчас пустой и не запускать новый reset по старому поручению.

`manage.py` поддерживает check/backup/reset. Он берёт ту же OS-блокировку, что приложение. Backup использует SQLite backup API, reset сначала сохраняет backup, создаёт и проверяет fresh DB, затем атомарно заменяет старую. Для reset нужен `--confirm-reset`, но это не постоянное разрешение пользователя на новые сбросы.

## 10. Проверки и команды

Последний завершённый полный прогон после исправлений progress/size: **94 теста, OK**. Ruff на изменённых файлах прошёл, форматирование выполнено. Это результат предыдущей сессии, не гарантия будущих правок.

В тестах намеренно встречаются логи `Contest delivery failed` и `TelegramNetworkError: connection lost`: это имитация ошибок для проверки outbox. Оценивать финальное `OK`/`FAILED`, а не один traceback в середине.

| Тестовый файл | Основное покрытие |
|---|---|
| `test_downloader.py` | Ссылки/бекенды/cookies/fallback, progress lock, гонка подсчёта размера |
| `test_instagram.py` | Instagram/cookies и ошибки |
| `test_media.py` | Подготовка медиа/FFmpeg |
| `test_launch.py` | Новые требования v4, планы, giveaways, maintenance, private picker, serialization |
| `test_planning.py` | Расписание, языки, progress, contests/outbox |
| `test_regressions.py` | Миграции, права, routing, скачивание и предыдущие регрессии |
| `test_worker.py` | Изоляция worker, отсутствие открытия рабочей БД, OS lock |

Запуск в PowerShell (если указанный путь ещё существует):

```powershell
$env:PYTHONIOENCODING = 'utf-8'
$py = 'C:\Program Files\WindowsApps\PythonSoftwareFoundation.Python.3.13_3.13.3824.0_x64__qbz5n2kfra8p0\python3.13.exe'
& $py -m ruff check bot.py config.py manage.py app services tests
& $py -m ruff format --check bot.py config.py manage.py app services tests
& $py -m unittest discover -s tests -q
& $py -m compileall -q app services bot.py config.py manage.py
& $py -m pip check
```

Следить за exit code каждой команды: PowerShell не всегда останавливает последующие команды после ошибки. Тесты используют временную/in-memory БД; нельзя ради их запуска перенастраивать production `.env`. Некоторые тестовые файлы импортируют соседние тестовые fixtures, поэтому предпочтителен `unittest discover -s tests`.

## 11. Linux: подготовлено, но не развёрнуто

Файлы: `deploy/LINUX.md`, `deploy/tautopbot.service`, `manage.py`, `.github/workflows/tests.yml`.

- Код: `/opt/tautopbot`; venv внутри этой папки.
- Данные: `/var/lib/tautopbot/bot.db`.
- Окружение: `/etc/tautopbot.env`.
- Пользователь: `tautopbot`, без root-прав.
- systemd: рестарт при ошибке, state directory, ограничения доступа, остановка process group.
- Внешний HTTP-порт не нужен, используется polling.
- Один процесс на токен/БД; OS lock не даёт запустить второй экземпляр с той же БД.
- При переносе не копировать Windows venv, caches, секреты в публичный архив или старую БД без необходимости.

В прошлой сессии не было доступного Linux/Docker/рабочего WSL для настоящего запуска systemd. **Не говорить «развёрнуто» или «проверено на сервере».** Нужны `systemd-analyze verify`, старт сервиса, журнал, Telegram smoke test и проверка прав на целевом Linux.

## 12. Правила продолжения без потери контекста

- Перед новой правкой читай соответствующий модуль и тесты, а не весь проект без необходимости.
- Новые tr-строки переводить в английский и казахский. Помимо base en.json/kk.json загружаются en_launch.json/kk_launch.json. Locale tests проверяют пропуски и placeholders.
- Не переводить пользовательский текст постов, имена каналов, призы и контактные данные.
- Сохранять UTF-8. PowerShell `Get-Content` без `-Encoding UTF8` раньше показывал кракозябры, хотя сами файлы были корректны.
- Не возвращать старые лимиты, автоматический trial или переход в личку по публичной Participate-кнопке.
- Не переписывать архитектуру на монолитный bot.py: сейчас это только entry point.
- Не сбрасывать БД и не удалять backup из-за удобства тестирования.
- Не считать отсутствие username у частного канала ошибкой; использовать chat_id и права.
- Не отключать network guard или проверку прав ради обхода ошибки.
- Не выполнять массовые рассылки/публикации при диагностике без соответствующего поручения пользователя.
- Все изменения предыдущего чата уже находятся на диске. Не «применять заново» описанные патчи.
- В следующем итоговом ответе по скачиванию разделить: что исправлено, что реально скачалось, прошли ли тесты и была ли проверена отправка Telegram.
