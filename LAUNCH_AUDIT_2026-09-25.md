# Аудит готовности к запуску — 25 сентября 2026

**Вывод: текущую версию нельзя считать готовой к масштабному публичному запуску.** Найдены воспроизводимые ошибки доставки, обработки платежей и очередей. Исправления не вносились. Изменённые ранее файлы проекта сохранены; в рамках аудита добавлены только диагностические скрипты и отчёты.

## Что фактически проверено

- Полный существующий комплект: **132 теста, все прошли**. Тесты используют изолированные базы и имитацию Telegram.
- Ruff lint: успешно. Компиляция Python: успешно. `pip check`: конфликтов установленных зависимостей не обнаружено.
- Ruff format check: **не прошёл**, один файл — `tests/test_launch.py`, около строки 79. Это мешает прохождению настроенного CI, хотя функциональные тесты проходят. Файл не исправлялся.
- Восемь дополнительных диагностических сценариев в `audit_probes.py`: **все восемь подтвердили описанные ниже дефекты/ограничения**. Их `OK` означает успешное воспроизведение проблемы, а не её отсутствие.
- Синтетическая нагрузка на временной SQLite: 2000 пользователей, сохранение пользователя и двух полей FSM; все записи сохранены. Время 9,778 с; максимальная пауза контрольной задачи event loop — 9,767 с. Это локальная проба БД/FSM на Windows, **не** оценка реальной пропускной способности Telegram или Linux-сервера.
- Рабочая SQLite: `integrity_check=ok`, `foreign_key_check` не вернул нарушений. Это проверка целостности, не доказательство корректности всех бизнес-связей.
- Живые read-only запросы Telegram: бот доступен, webhook не задан; подтверждено администраторство в 10 известных чатах. Ещё один сохранённый адрес не удалось проверить. На момент проверки было 2 ожидающих обновления.
- Проверенная резервная копия: `backups/bot-20260925T062220361530Z.sqlite3`.

## Подтверждённые проблемы

### 1. Отложенный пост не повторяется после временного ограничения Telegram — высокая важность

`app/features/posts.py:850–972`, `app/scheduler.py:21–40`.

Перед отправкой расписание выключается. `TelegramRetryAfter` переводит получателя в `failed`; итоговый пост тоже становится `failed`. Планировщик выбирает только `scheduled`, поэтому после окончания ограничения автоматической повторной попытки нет.

Воспроизведение: Telegram отвечает RetryAfter; два вызова планировщика дают только одну попытку отправки, `scheduled_posts.active=0`. Пользователь ожидает публикацию по расписанию, но должен обнаружить сбой и повторить вручную.

Нужно: отложенная повторная попытка для однозначно не выполненных запросов с соблюдением `retry_after`; неопределённые сетевые результаты обрабатывать отдельно, без слепого повтора.

### 2. Оплата заблокированного пользователя может быть принята, но не обработана — высокая важность

`app/features/payments.py:pre_checkout`, `app/middleware.py:31`.

Проверка существующего счёта допускает checkout независимо от блокировки пользователя. Middleware отбрасывает все последующие сообщения заблокированного пользователя, включая `successful_payment`.

Воспроизведение: счёт существует, пользователь заблокирован; checkout получает `ok=True`, обработчик successful_payment не вызывается, заказ остаётся `pending`. Реальное списание Stars не проводилось: проверена логика через имитацию Telegram.

Нужно: обрабатывать финансовые события независимо от блокировки обычного интерфейса; отдельно определить политику оплаты заблокированными пользователями.

### 3. Один недоступный получатель альбома задерживает остальных — высокая важность

`app/features/sources.py:126`, функция `flush_albums`.

В обработке очереди нет изоляции ошибок каждой записи. Если отправка выбора получателей для первого готового альбома получает Forbidden, функция завершается до удаления этой записи и до обработки последующих альбомов.

Воспроизведение: два пользователя; бот заблокирован первым. Два запуска очереди оба обращаются только к первому; второй альбом не обрабатывается. Ошибка повторяется при следующем запуске.

Нужно: независимая обработка записей очереди и явный статус/политика повторов для недоступного получателя.

### 4. Заявки заблокированных пользователей могут перекрыть проверку следующих заявок — высокая важность при большом потоке

`app/scheduler.py:164`, `app/features/conditions.py:check_request`.

Планировщик выбирает первые 100 pending-заявок по `last_checked`. Для заблокированных пользователей `check_request` возвращается до изменения `last_checked` или статуса. Эти записи снова занимают всю выборку.

Воспроизведение: первые 100 заявок относятся к заблокированным пользователям, 101-я — обычная. Два запуска выполняют 200 проверок первых заявок, но ни разу не доходят до 101-й.

Нужно: исключать заведомо необрабатываемые записи из выборки либо переводить их в отдельное состояние с подходящей политикой возврата.

### 5. Рассылка прерывается на RetryAfter и теряет возможность продолжения — высокая важность для публичного запуска

`app/features/admin.py:270`.

Черновик рассылки удаляется до отправки; FSM очищается. Цикл ловит BadRequest/Forbidden, но не RetryAfter или сетевую ошибку. Поадресного сохранённого прогресса нет.

Воспроизведение: первая отправка получает RetryAfter; рассылка прерывается, черновик отсутствует, FSM пуст. При сбое в середине списка безопасно продолжить только с неотправленных адресатов текущим механизмом нельзя.

Нужно: сохраняемая очередь рассылки с прогрессом, обработкой лимитов и неопределённых исходов.

### 6. Очередь отложенных постов ограничена 20 постами за проход — ограничение масштабирования

`app/scheduler.py:23`, `app/application.py:51–70`.

За проход выбираются 20 постов, проход запускается раз в 10 секунд; отправки внутри последовательные. `max_instances=1` не позволяет запускам перекрываться.

Воспроизведение: из 100 одновременно просроченных постов вызвано ровно 20 публикаций. Даже при мгновенном API требуется пять проходов. Если обработка сама занимает больше интервала, ожидание возрастает. Проверка прав добавляет несколько API-вызовов на каждого получателя (`app/access.py:owner_and_bot_ok`).

Нужно: определённые требования по допустимому опозданию, нагрузочный тест с реалистичными задержками и управляемая очередь доставки. Простое увеличение LIMIT не решает лимиты Telegram.

### 7. Проверка подписок перед выбором победителей начинается заново после ошибки — ограничение надёжности крупных конкурсов

`services/contests.py:262–292`.

Проверки участников последовательные, прогресс не сохраняется. Запись результатов начинается только после полного успешного прохода. При сетевом сбое или RetryAfter на позднем участнике следующий запуск вновь проверяет всех с начала.

Воспроизведение: 100 участников, ошибка на 51-м. Две попытки дважды проверяют первого и ни разу не доходят до 52-го. Конкурс остаётся `closing`.

Нужно: управляемые повторы и масштабируемая проверка с чёткой политикой актуальности подписок к моменту розыгрыша; не ослаблять проверку условий ради ускорения.

### 8. Долгое завершение одного конкурса задерживает следующие — ограничение масштабирования

`services/contests.py:506`, функция `tick`.

Все конкурсы обслуживаются последовательным циклом. Пока `finish` одного конкурса проверяет участников, код не приступает к публикации следующего; доставка outbox также расположена после этого цикла.

Воспроизведение: первый конкурс остановлен в медленной проверке; второй, уже готовый к публикации, остаётся `scheduled` и не отправляется до завершения первого.

Нужно: разделить независимые очереди публикации, проверки итогов и выдачи, сохранив защиту от повторного выбора победителей.

### 9. Синхронная SQLite блокирует основной цикл событий — подтверждено нагрузочной пробой

`app/database.py:15–38`, `app/storage.py`, `app/accounts.py:ensure_user`.

Асинхронные обработчики напрямую выполняют синхронные SQL-запросы и commit. В пробе 2000 конкурентных операций сохранения произошла пауза event loop 9,767 с. Отдельная проба внешней блокировки записи при тестовом busy_timeout 250 мс синхронно заняла 0,321 с; рабочее соединение настроено на timeout 30 с.

Это не означает, что каждый запрос занимает столько времени. Это показывает, что всплеск обращений или ожидание блокировки БД задерживает другие задачи того же процесса.

Нужно: определить целевую нагрузку, убрать блокирующую работу из event loop и затем повторить измерения. Переход на другую СУБД сам по себе не заменяет корректной организации очередей и транзакций.

### 10. Текущая проверка форматирования в CI не проходит — низкая важность

`tests/test_launch.py`, около строки 79; `.github/workflows/tests.yml` (проверка `ruff format --check` в имеющемся workflow).

Ruff сообщает о необходимости переформатирования одного файла. Функциональные тесты проходят. Исправление не применялось по просьбе пользователя.

## Эксплуатационные пробелы и пределы проверки

- Есть systemd unit и инструкция Linux. Локально Linux/WSL-дистрибутив не доступен; Docker не найден. Проверить настоящий старт systemd, его ограничения, FFmpeg/Deno и права файлов в Linux не удалось.
- CI описывает Windows/Ubuntu и Python 3.11/3.13, но результаты удалённых запусков CI в этом аудите не получены. Локальные тесты выполнены Python 3.13 на Windows.
- В загрузчике ограничены две одновременно выполняемые задачи; общей ограниченной очереди приёма и отдельного лимита проверки ссылок не видно. При массовом потоке это риск роста очереди, а не измеренная пропускная способность.
- Зависимости заданы диапазонами, точный воспроизводимый набор не зафиксирован. `pip check` проверяет совместимость, а не уязвимости. Аудит публичных advisories здесь не проводился.
- Есть ручной backup/reset, но автоматическая копия вне сервера, проверка восстановления по расписанию и внешнее уведомление о простое не подтверждены.
- Нет заданной целевой нагрузки: пользователей одновременно, постов в минуту, размера конкурсов, скачиваний и допустимого опоздания. Обещать готовность к неопределённому «масштабу» нельзя.
- Не выполнялись реальные публикации/удаления, реальные платежи, приём заявок вторым аккаунтом или скачивания с внешних площадок: тестовый чат не был указан. Проверки с имитацией API не выдаются за живой end-to-end тест.

## Выход из чатов и очистка

Резервная копия создана и проверена до обслуживания. Telegram подтвердил успешный выход из **10 известных каналов/групп**. Для одиннадцатого сохранённого адреса вернул `Bad Request: chat not found`; членство в нём не подтверждено. Один временный сетевой сбой устранён повторной попыткой выхода, без изменения кода приложения. Точные ответы находятся в `audit_leave_results.json`. Работа выполнена отдельным одноразовым скриптом `audit_leave_chats.py`. Telegram API не предоставляет перечень всех чатов бота, поэтому нельзя гарантировать выход из чатов, о которых нигде в сохранённых данных нет сведений.

**Рабочая БД ещё не сброшена:** ожидается ответ на уже заданный вопрос, нужен ли полный сброс с пользователями, платежами, Premium и настройками или только каналы и публикации. Это два разных объёма удаления. Проверки на чистой изолированной БД выполнены; повторная проверка именно рабочей БД после сброса пока не выполнялась.

Бот не запускался. Ожидающие Telegram updates не удалялись. До согласованного сброса база продолжает содержать прежние связи каналов, уже не соответствующие членству после выхода.
